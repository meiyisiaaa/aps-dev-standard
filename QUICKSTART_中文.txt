APS 一键安装
===========

仓库创建后先执行一次：

python scripts/configure_repository.py OWNER/REPO

git status --short
# 检查变更后，只暂存本次发布文件：
git add -- <已审查文件>
git diff --cached --check
git commit -m "Configure APS distribution"
git push

git tag v1.3.4
git push origin v1.3.4

之后任何机器：

macOS / Linux：
curl -fsSL https://raw.githubusercontent.com/meiyisiaaa/aps-dev-standard/main/install.sh | sh

Windows PowerShell：
irm https://raw.githubusercontent.com/meiyisiaaa/aps-dev-standard/main/install.ps1 | iex

安装器会校验 Release 的 SHA-256；没有可验证的 Release 时默认失败。
临时允许使用 main 源码包：设置 APS_ALLOW_MAIN_FALLBACK=1 后再执行安装命令。

安装后进入项目：

aps

第一次使用：

新项目运行：
aps init --no-launch

已有项目运行：
aps resume --no-launch

把 CLI 输出的完整 APS Agent Handoff 代码块发送到当前 Agent Host。Bootstrap 完成后运行：
aps doctor
aps status

Bootstrap 时必须让用户确认项目风险级别并写入 .ai/project-profile.json：NORMAL（普通）、LARGE（大型）或 REGULATED（强合规）。所有项目维护 .ai/audit/transitions.jsonl；大型项目按模块或工作流填写 workstreams；Stage 20 Release 前按级别补齐 .ai/release-readiness.json。风险级别不增加 Stage。普通 Stage 满足 Artifact、验收、Verification 和 blocker 条件后，可直接记录 COMPLETE + PASS 并进入 Transition Contract 指定的下一 Stage，不要求用户额外确认“Stage PASS”；用户决策、重大范围 / 方向变化、HOLD / STOP 和 Release approval 仍需确认。

遇到阻塞后的恢复：
1. 先运行 aps status，只执行输出的唯一 NEXT。
2. 运行状态缺失或无法解析时，先运行 aps doctor --standard-only 获取第一项问题；doctor 不会自动修复坏状态，需人工修复 .ai/state.yaml 后再运行 aps resume --no-launch；损坏状态不会被猜测为 NORMAL。
3. 普通已有项目用 aps resume；只有 APS 半安装或损坏残留用 aps upgrade 修复；空目录用 aps init。
4. Standard 版本不匹配或托管文件冲突时，先人工合并 .ai/incoming/<version>/，再运行 aps upgrade；不要自动合并本地修改。
5. 除非明确接受备份后覆盖，不要使用 --force-managed。
6. 待决策时运行 aps decision show/list，在当前对话完成决策卡分析，再运行 aps decision answer 或 aps decision cancel。
7. 风险基线、Transition 审计或 Release readiness 损坏时，APS 会拒绝继续；按 status / doctor 输出的唯一 NEXT 修复，不要猜测为 NORMAL 或手动把 Gate 改成 PASS。

交接时只携带当前 Stage / Task 和直接引用；Stage User Brief 只在完成、阻塞、暂停或切换对话时输出，不要每轮重复。完成结果必须提醒下一 Stage，以及目标 Stage 是否需要先打开 Plan 模式。大型项目可以并行 Task，但全局状态、Gate、Decision 和 Registry 仍由 Coordinator 统一维护。

增量变更：已确认 Scope / Requirements 内且不改变已确认契约的小 Task 留在当前 Stage，只更新差异并做定向验证；新增行为、修改已通过 Gate 的内容或改变技术 / 安全 / Release 约束时进入 Stage 22，使用 `.ai/templates/change-log.md` 做 Impact Analysis，返回最早受影响 Stage。保留未受影响的有效 Artifact；依赖不清楚时扩大验证，不能用小改动绕过 Gate。

常用：
aps init        新项目
aps resume      首次接管旧项目，之后只恢复状态
aps rebaseline  旧项目从 Stage 01 重新审查（需运行状态和 --confirm）
aps doctor      项目体检
aps status      查看状态
aps upgrade     升级 Standard
aps research brief <调研 Artifact>  输出 Research Brief
PRD 汇总        不新增 PRD 阶段；按需从 .ai/templates/prd-snapshot.md 创建 Stage 08 派生视图

需要重大产品、技术、UX 或 Scope 决策时：

aps decision request .ai/cycles/CYCLE-001/stages/01-idea/decision-requests/DEC-001.json

统一在当前对话中提出结构化决策问题。提问前必须逐项说明每个选项的优点、缺点、适用条件和主要风险；如果给出推荐，必须说明推荐依据以及什么新证据会改变推荐。完整候选项保留在 Decision Request 中，不限制为 2~3 个选项；多选、排序、自由输入或复杂决策可分轮提问或直接使用自由文本。

用户回答后记录：

aps decision answer DEC-001 A
aps decision list
aps decision show DEC-001
aps decision cancel DEC-001 --reason "范围已调整"

用户选择不等于 Gate 通过，仍需完成 Artifact 和 Validation。

切换对话后运行 `aps status` 或 `aps resume --no-launch`，查看当前 Cycle、阻塞项、待决策和下一步。

以下 Stage 进入时必须先打开 Codex Plan 模式：01、05、06、07、08、09、10、13、14、15、16、20；Stage 22 有 Active Change 时也必须打开。计划确认后可切回普通模式执行。`aps status` 会显示 `Mode gate`；Codex Host 不会在未满足要求时自动启动普通会话。

保护规则：
- 不要重复执行 init；已有 APS 文件时会拒绝。
- resume 不会重复安装或升级 Standard。
- 只有 upgrade 会更新已安装的 Standard 文件。
- 相同版本重复 upgrade 不应修改工作区。
