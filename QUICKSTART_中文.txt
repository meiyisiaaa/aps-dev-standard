APS 一键安装
===========

仓库创建后先执行一次：

python scripts/configure_repository.py OWNER/REPO

git status --short
# 检查变更后，只暂存本次发布文件：
git add -- <已审查文件>
git diff --cached --check
git commit -m "Configure APS distribution"
git push

git tag v1.3.7
git push origin v1.3.7

之后任何机器：

macOS / Linux：
curl -fsSL https://raw.githubusercontent.com/meiyisiaaa/aps-dev-standard/main/install.sh | sh

Windows PowerShell：
irm https://raw.githubusercontent.com/meiyisiaaa/aps-dev-standard/main/install.ps1 | iex

安装器会校验 Release 的 SHA-256；没有可验证的 Release 时默认失败。
临时允许使用 main 源码包：设置 APS_ALLOW_MAIN_FALLBACK=1 后再执行安装命令。

安装后进入项目：

aps

第一次使用：

新项目运行：
aps init

已有项目运行：
aps resume

默认由 APS 恢复或启动 Host；需要只输出可复制的 APS Agent Handoff 时再加 `--no-launch`。Bootstrap 完成后运行：
aps doctor
aps status

项目风险级别、Transition audit 和 Release readiness 都是可选元数据；存在时检查，缺失或过期只提示 WARN，不猜测为 NORMAL。普通 Stage 完成实际工作和相关验证后可记录 COMPLETE + PASS 并按需继续；待处理用户决策、明确 HOLD / STOP、安全边界、Release approval，以及 Stage 17 缺少 active task 仍保留为暂停条件。

遇到问题后的恢复：
1. 先运行 aps status 查看提示；NEXT 是建议，不要求唯一或必须执行。
2. 运行状态缺失或无法解析时，先运行 aps doctor --standard-only 获取第一项问题；doctor 不会自动修复坏状态，需人工修复 .ai/state.yaml 后再运行 aps resume --no-launch；损坏状态不会被猜测为 NORMAL。
3. 普通已有项目用 aps resume；只有 APS 半安装或损坏残留用 aps upgrade 修复；空目录用 aps init。
4. Standard 版本不匹配或托管文件冲突时，先人工合并 .ai/incoming/<version>/，再运行 aps upgrade；不要自动合并本地修改。
5. 除非明确接受备份后覆盖，不要使用 --force-managed。
6. 待决策时运行 aps decision show/list，在当前对话确认问题，再运行 aps decision answer 或 aps decision cancel。
7. 风险基线、Transition 审计、Release readiness、PRD Snapshot 或 Registry 缺失/过期/普通内容不完整时，APS 给出 WARN 并继续；路径、链接、不可安全读取、运行状态、manifest 和托管文件完整性问题仍会拒绝继续。不要猜测为 NORMAL 或手动把 Gate 改成 PASS。

任务执行硬规则：`继续` 只延续当前已明确授权的任务，不授权新任务，也不会按列表自动选择下一个任务。Stage 17 必须记录 `active_task_ref` 和 `active_task_kind`；只有 `implementation` 且预计修改生产代码或测试的任务才算进入开发。没有 READY 的 implementation 任务时，直接报告并请求具体 TASK-ID，不得用审计、文档、升级或无关验证制造进度。

交接时携带当前 Stage / Task 和直接引用即可；Stage User Brief 有帮助时再输出，不要每轮重复。复杂任务可先写简短计划，但计划不是固定门禁。大型项目可以并行 Task，但全局状态、Gate、Decision 和 Registry 仍由 Coordinator 统一维护。

增量变更：已确认 Scope / Requirements 内且不改变已确认契约的小 Task 留在当前 Stage，只更新差异并做定向验证；只有实际改变契约、Scope 或下游影响时，才使用 Stage 22 和 `.ai/templates/change-log.md` 记录并路由。保留未受影响的有效 Artifact；依赖不清楚时扩大验证。

常用：
aps init        新项目
aps resume      首次接管旧项目，之后只恢复状态
aps rebaseline  旧项目从 Stage 01 重新审查（需运行状态和 --confirm）
aps doctor      项目体检
aps status      查看状态
aps upgrade     升级 Standard
aps research brief <调研 Artifact>  输出 Research Brief
PRD 汇总        不新增 PRD 阶段；按需从 .ai/templates/prd-snapshot.md 创建 Stage 08 派生视图

需要重大产品、技术、UX 或 Scope 决策时：

aps decision request .ai/cycles/CYCLE-001/stages/01-idea/decision-requests/DEC-001.json

统一在当前对话中提出清晰的决策问题。复杂选择可说明选项取舍、证据和确认方式；简单问题可直接使用自由文本。Decision Request 最小保留问题、状态、Cycle/Stage、input_type、schema_version 和 id；候选项、推荐、影响和 Decision Card 按需填写。

用户回答后记录：

aps decision answer DEC-001 A
aps decision list
aps decision show DEC-001
aps decision cancel DEC-001 --reason "范围已调整"

用户选择不等于 Gate 通过，仍需完成 Artifact 和 Validation。

切换对话后运行 `aps status` 或 `aps resume --no-launch`，查看当前 Cycle、阻塞项、待决策和下一步。

复杂任务可以先写简短计划；没有计划或原生 Codex Plan 模式不可用时仍可启动普通会话。Stage 22 按实际影响使用，不是固定入口门禁。

保护规则：
- 不要重复执行 init；已有 APS 文件时会拒绝。
- resume 不会重复安装或升级 Standard。
- 只有 upgrade 会更新已安装的 Standard 文件。
- 相同版本重复 upgrade 不应修改工作区。
