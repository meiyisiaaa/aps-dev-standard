使用本项目内的 AI Project Standard 作为开发参考：

- Lifecycle Standard：`.ai/standards/lifecycle.md`
- Artifact & State Standard：`.ai/standards/artifact-state.md`

第一次使用：
1. 新项目从 `aps init` 开始；已有项目从 `aps resume` 开始；只想复制 handoff 时加 `--no-launch`。`init` 不覆盖旧项目。
2. 将 CLI 打印的完整 `APS Agent Handoff` 代码块发送到当前 Agent Host。
3. Bootstrap 后运行 `aps doctor` 和 `aps status`，确认当前 Cycle、Stage、Gate、blocker 与提示。

APS CLI 边界：`resume` 负责接管或恢复，`upgrade` 只更新 Standard；空目录使用 `init`。托管文件冲突先人工比较 `.ai/incoming/<version>/`，不自动合并；只有明确接受备份后覆盖时才使用 `--force-managed`。运行状态损坏、项目路径不安全、manifest 或托管文件完整性失败时，先修复安全问题。

治理原则：
- 23 个 Stage/Gate 用于导航和状态记录；普通流程条件、计划、风险档案、Registry、Transition audit、Release readiness、PRD Snapshot、Research Brief、Stage User Brief、Artifact Contract 和 Change 记录按实际需要使用，缺失或过期只提示。
- 不自动猜测 `NORMAL`，不自动通过 Gate，不自动覆盖用户文件。普通任务可以继续；只有待处理 `user_decision`、明确 `HOLD` / `STOP`、安全/完整性错误，或 `EXECUTION_LOOP` 没有 active task 时暂停。
- `status`、`doctor` 和 handoff 的 `NEXT` 是可选建议，不要求唯一或必须执行。
- 全局治理写入仍遵守 Single Writer、revision、锁和 compare-before-write；实际需要保留的 Artifact、状态变更和验证证据必须落盘。

Task routing guard（任务路由硬规则）：
- “继续”只表示继续当前已明确授权的任务；它不授权新任务，也不允许按任务列表顺序、优先级、依赖或“下一个”自动挑选任务。
- 在 `EXECUTION_LOOP` 中，只有用户明确给出 `TASK-*` 后，才能在 `.ai/state.yaml` 设置 `active_task_ref` 和 `active_task_kind`。没有 active task 时必须停下并请求明确任务，不得按任务列表自动挑选，也不得先写审计、架构或其他替代物。
- 只有 `active_task_kind=implementation` 且任务明确预计修改生产代码或测试，才可称为“进入开发”。`verification`、`governance`、`external` 任务必须明确标注，不得冒充开发。
- 待决策只暂停受影响的业务路径，但不得用无关任务填充空档；当前没有 READY 的 implementation 任务时，直接报告并请求一个具体开发目标。

恢复提示：
- 状态缺失或无法解析时运行 `aps doctor --standard-only`，人工修复 `.ai/state.yaml` 后再运行 `aps resume --no-launch`。
- Standard 版本较旧、可选元数据缺失或不完整时，APS 会给出 WARN 并继续；需要更新时显式运行 `aps upgrade`。
- 待决策时用 `aps decision show/list` 查看问题，回答或取消后运行 `aps decision answer/cancel`；回答只解除对应 blocker，不自动改变 Gate。

Bootstrap 顺序：
1. 检测 repo root、项目类型、当前 Agent Host 和生效的项目指令链。
2. 按最小上下文读取两份 Standard 和当前 Stage 所需章节；不预加载旧 Cycle 或无关 Artifact。
3. 读取或初始化 `.ai/state.yaml` 和 active cycle；按需读取或初始化 `.ai/decisions.md`、`.ai/registry.yaml`，已有内容不得无理由覆盖。
4. `.ai/project-profile.json`、`.ai/audit/transitions.jsonl`、`.ai/release-readiness.json` 等元数据存在时检查；缺失或过期记录 WARN，不猜测内容。
5. 检测当前 Host，并按需读取或初始化 `.ai/runtime/hosts/<HOST-ID>.yaml`。
6. 从 state 恢复 Cycle、Stage/Stage Type、stage_status、gate_status、Scope、blockers、Active Change、Pending Decision refs 和 revision。
7. 需要审计时追加 Transition 记录，不删除或改写历史；审计是记录和校验辅助，不是普通流程的启动门禁。
8. 已有项目先读取实际代码和有效 Artifact，判断真实工作位置；不要把旧项目伪装成新项目，也不要默认从 Build 开始。
9. 局部变更留在当前 Stage 并做相关验证；只有实际改变已确认契约、Scope 或下游影响时，才使用 `.ai/templates/change-log.md` 记录影响并路由到受影响 Stage。Stage 22 是可用的变更记录路由，不是固定前置门禁。
10. 使用 Agent Skill 时检查路径、结构、同名冲突和可用性；未验证的 Skill 不得假装生效。
11. 文档、代码、状态、Skill 与已确认 Decision 冲突时，保留 `user_decision` blocker，等待用户处理，不自行猜测。
12. 执行当前已明确授权的任务和验证；没有 active task 时不要自动挑选任务，不因普通记录缺失而停止，也不一次执行整个开发周期。
13. 全局治理写入使用 Single Writer、锁、revision 和 compare-before-write；并行任务不得覆盖共享状态。
14. 只有明确 HOLD/STOP、待处理用户决策、安全错误、用户要求的确认，或 `EXECUTION_LOOP` 没有 active task / 当前任务结束或阻塞时暂停。普通 Stage 完成后可按 Transition Contract 记录状态，不要求额外的唯一 NEXT、计划或“Stage PASS”确认。
15. 需要交接时可输出简短 Stage User Brief；需要产品单页时可按需从 Stage 08 Artifact 生成 PRD Snapshot。两者都是辅助记录，不替代实际代码、Artifact 和验证。

研究和决策：
- Research 可在当前对话直接回答并按需落盘完整报告；`aps research brief <ARTIFACT>` 会展示已有摘要。字段不完整时提示补充，不阻塞安全的普通工作。
- Decision Request 的最小必填字段是 `question`、`status`、`cycle`、`stage` 和 `input_type`（另含 schema/id）；options、tradeoffs、recommendation、decision_card 和 impact 按问题需要填写。待处理请求仍暂停对应业务路径。
- 用户回答后运行 `aps decision answer <DECISION-ID> <ANSWER>`；它只解除对应 blocker，Gate 仍由 Agent 根据实际 Artifact 和验证更新。

涉及前端/UI 时，Registry、Design System、Token、Component、Pattern、Motion 和项目 Skill 有记录则优先复用；缺失时记录提示并使用已验证的项目能力。

只在聊天中宣称完成不等于已经落盘；凡是实际需要作为状态、Artifact 或验证证据的内容，都要写入对应文件并检查写入结果。
